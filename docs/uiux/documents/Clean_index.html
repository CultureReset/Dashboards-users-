02 · Node + box

What actually exists physically and in the cloud

Ghost Node is the stable execution concept. It can be a small physical box at the business, an isolated cloud worker, a Mac/PC, or a hybrid. Android can be physically attached to the node or provisioned as a cloud Android environment.

The same dashboard controls all forms. The owner should not care whether a capability is fulfilled by a physical Android, cloud Android, browser or official provider route.

11 · Trust + proof

A click is not success. Verified state is success.

Every consequential task ends by rereading the destination or authoritative source, comparing expected versus actual, capturing evidence, and creating a receipt.

Outcomes: VERIFIED · PARTIAL · UNKNOWN · FAILED. If Ghost cannot prove it, it should not claim success.

13 · Developer wiring

How every visible page connects to Ghost Core

Frontend pages request normalized reads and semantic commands. They never directly drive Android, browser automation, or vendor APIs.

Permanent contract: Screen → Application API → canonical/read model → capability → permission → target → executor → verify → evidence → ledger → live UI status.
1ScreenDashboard / mobile / public UI
2Application APIStable business-facing contract
3Canonical contextBusiness, location, source truth
4CapabilitySemantic outcome
5PolicyScope + AUTO/ASK/NEVER
6Target resolverWhich connected system/account
7Executor registryAPI / browser / Android / desktop
8VerificationExpected vs actual reread
9LedgerReceipt + evidence + events

Canonical data plane

Business profile, locations, products/services, menus, events, availability, customers and public blocks are vendor-independent.

Execution plane

Providers and executors translate semantic capabilities into a specific API/browser/Android/desktop action without leaking that detail into app UI.

Proof plane

Verification, evidence, idempotency, retries, resume state, human takeover and compatibility are shared services, not reimplemented per app.
